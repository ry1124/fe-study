## 第6章 データベース

たくさんのデータを、表の形で整理して保存し、取り出す仕組み（データベース）と、その操作の言葉（SQL）を学びます。

> **この章のゴール**
> ・主キーと外部キーの意味が分かる
> ・正規化（表の分け方）の考え方が分かる
> ・簡単な SQL を読んで、結果の行を答えられる
> ・トランザクションと障害からの回復の方法が分かる

### ① 関係データベースの基本

#### イメージ
Excel の表のように、データを行と列で管理します。

| 社員番号 | 氏名 | 部署コード |
| --- | --- | --- |
| 1 | 佐藤 | A1 |
| 2 | 鈴木 | B2 |

- **表**（テーブル）：データの入れ物。例：「社員」表
- **行**（レコード）：1件分のデータ。例：佐藤さんの行
- **列**（項目）：データの種類。例：「氏名」の列

#### 主キー
行を1つに決めるための列です。同じ値が2つあってはいけません。空（NULL）も不可です。
例：社員番号（同じ番号の社員はいない）。氏名は同姓同名がありうるので主キーに向きません。

#### 外部キー
**他の表の主キー**を参照する列です。
例：「社員」表の部署コードが、「部署」表の主キー（部署コード）を参照する。
→ 部署表にない部署コード（例：Z9）を社員表に入れることはできません（**参照制約**）。

### ② E-R 図

データベースを作る前に、どんなデータ（**エンティティ**）があり、それらがどう関係しているか（**リレーションシップ**）を描いた図です。
- **1対多**：1つの部署に、多くの社員がいる
- **多対多**：1人の学生が多くの科目を取り、1つの科目を多くの学生が取る

> **多対多の表し方**：間に「履修（学生番号, 科目番号）」のような表を作り、1対多の関係2つに分けます。

### ③ 正規化（表を分ける作業）

#### なぜ表を分けるの？
次の表を見てください。

| 受注番号 | 商品番号 | 商品名 | 数量 |
| --- | --- | --- | --- |
| 1 | P1 | りんご | 3 |
| 2 | P1 | りんご | 5 |

「P1 ＝ りんご」が何度も出てきます。商品名を「青りんご」に変えたいとき、全部の行を直さないと、データが食い違ってしまいます。そこで「商品（商品番号, 商品名）」の表に分ければ、1か所直すだけで済みます。これが**正規化**です。

#### 関数従属
「X が決まれば、Y が1つに決まる」ことを「Y は X に関数従属する」といい、X → Y と書きます。例：商品番号 → 商品名

#### 正規化の段階
| 段階 | すること |
| --- | --- |
| 第1正規形 | 1つのマスに1つの値だけにする（繰り返しをなくす） |
| 第2正規形 | **主キーの一部だけで決まる列**を、別の表に分ける |
| 第3正規形 | **主キー以外の列で決まる列**を、別の表に分ける |

#### 例題
「受注明細（受注番号, 商品番号, 商品名, 数量）」、主キーは {受注番号, 商品番号} の組
- 商品名は「商品番号」だけで決まる → 主キーの一部で決まっている → 第2正規形にするため「商品（商品番号, 商品名）」に分ける

「社員（社員番号, 氏名, 部署コード, 部署名）」、主キーは社員番号
- 部署名は「部署コード」で決まる → 主キー以外の列で決まっている → 第3正規形にするため「部署（部署コード, 部署名）」に分ける

### ④ 関係演算

| 演算 | すること | たとえ |
| --- | --- | --- |
| 選択 | 条件に合う**行**を取り出す | 営業部の人だけ |
| 射影 | 指定した**列**を取り出す | 氏名の列だけ |
| 結合 | 2つの表を共通の列でつなぐ | 社員表と部署表を部署コードでつなぐ |

> **覚え方**：「選択は横（行）、射影は縦（列）」。

### ⑤ SQL

SQL は、データベースに命令する言葉です。

#### 基本の形
```
SELECT 氏名, 給与
  FROM 社員
  WHERE 部署 = '営業'
  ORDER BY 給与 DESC
```
読み方：「社員表（FROM）から、部署が営業の行（WHERE）の、氏名と給与（SELECT）を、給与の大きい順（ORDER BY … DESC）に並べて取り出す」

#### グループにまとめる
```
SELECT 部署, AVG(給与)
  FROM 社員
  GROUP BY 部署
  HAVING AVG(給与) >= 30
```
読み方：「部署ごとにまとめて（GROUP BY）、平均給与が30以上の部署（HAVING）について、部署名と平均給与を取り出す」

| 句 | 意味 |
| --- | --- |
| WHERE | まとめる**前**の、行の条件 |
| GROUP BY | 同じ値ごとにまとめる |
| HAVING | まとめた**後**の、グループの条件 |
| ORDER BY | 並べ替え（ASC は小さい順、DESC は大きい順） |

#### 集計の関数
COUNT（数）、SUM（合計）、AVG（平均）、MAX（最大）、MIN（最小）

#### 条件の書き方
- LIKE '東%'：「東」で始まる（% は何文字でもよい、_ はちょうど1文字）
- BETWEEN 10 AND 20：10以上20以下
- IN ('A', 'B')：A か B のどちらか
- IS NULL：値が空

#### 例題
社員表：(1, 営業, 30)、(2, 営業, 26)、(3, 開発, 40)、(4, 開発, 36)、(5, 総務, 28)
```
SELECT 部署 FROM 社員 GROUP BY 部署 HAVING AVG(給与) >= 30
```
① 部署ごとの平均：営業 28、開発 38、総務 28
② 30以上は開発だけ
③ 結果：**開発**

#### その他の操作
- 追加：INSERT INTO 表 VALUES (…)
- 変更：UPDATE 表 SET 列 = 値 WHERE …
- 削除：DELETE FROM 表 WHERE …
- **ビュー**：SELECT の結果に名前を付けた仮想の表（見せる列を限定できる）

### ⑥ トランザクション

#### イメージ
銀行の振込は「Aさんの口座から引く」と「Bさんの口座に入れる」の2つで1組です。片方だけ成功するとお金が消えてしまいます。このような「ひとまとまりの処理」を**トランザクション**といいます。

#### ACID 特性
| 名前 | 意味 |
| --- | --- |
| 原子性（A） | 全部やるか、全部やらないかのどちらか |
| 一貫性（C） | データの決まりが守られる（残高がマイナスにならない など） |
| 独立性（I） | 同時に動いても、お互いに影響しない |
| 永続性（D） | 確定した結果は、障害が起きても消えない |

- **コミット**：処理を確定する
- **ロールバック**：処理を取り消して、元に戻す

#### 排他制御（ロック）
2人が同時に同じデータを書き換えると、片方の更新が消えてしまいます。そこで、使っている間は他の人が触れないように**ロック（鍵）**をかけます。
- **共有ロック**：読むだけ。他の人も読める
- **専有ロック**：書く。他の人は読むことも書くこともできない

> **デッドロック**：2つのトランザクションが、お互いにロックの解除を待って止まる状態。ロックをかける順番をそろえると防げます。

### ⑦ 障害からの回復

データベースは、更新の記録（**ログ**）を残しています。
- **更新前ログ**：書き換える前の値
- **更新後ログ**：書き換えた後の値

| 回復の方法 | 使うログ | いつ使う |
| --- | --- | --- |
| ロールバック | 更新前ログ | 確定していない処理を取り消すとき |
| ロールフォワード | 更新後ログ | ディスクが壊れたとき。バックアップを戻した後、その後の更新をやり直す |

- **チェックポイント**：一定の間隔で、メモリの内容をディスクに書き出した時点。障害のとき、チェックポイント以降のログだけ処理すればよいので、回復が速くなります。

### ⑧ データの活用

- **データウェアハウス**：分析のために、整理したデータをためておく倉庫
- **データマイニング**：大量のデータから、規則性（「この商品とこの商品は一緒に買われやすい」など）を見つける
- **NoSQL**：表の形にこだわらないデータベース。大量のデータを速く扱える

### この章のまとめ

- 主キーは行を1つに決める列。外部キーは他の表の主キーを参照する列
- 第2正規形は「主キーの一部で決まる列」、第3正規形は「主キー以外で決まる列」を分ける
- 選択は行、射影は列
- WHERE はまとめる前、HAVING はまとめた後の条件
- ACID：原子性・一貫性・独立性・永続性
- ロールバックは更新前ログで取り消し、ロールフォワードは更新後ログでやり直し
