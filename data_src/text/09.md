## 第9章 開発技術

システムを作る手順（開発の進め方）、設計の考え方、テストの方法を学びます。

> **この章のゴール**
> ・ウォーターフォールとアジャイルの違いが分かる
> ・オブジェクト指向の用語（カプセル化・継承・多態性）を説明できる
> ・テストの種類と、テストデータの選び方（同値分割・限界値分析）が分かる

### ① 開発の進め方

#### ウォーターフォール
**イメージ**：滝の水が上から下に流れるように、工程を順番に進めます。
要件定義 → 設計 → プログラミング → テスト → 運用
- 前の工程に戻らない前提で、計画を立てやすい
- 途中で「やっぱりこうしたい」という変更に弱い

#### アジャイル
**イメージ**：小さく作って見せて、直して、また作る、を短い期間で繰り返します。
- 1〜4週間くらいの区切り（**スプリント**、イテレーション）ごとに、動くものを作る
- 変更に強い

#### アジャイルの代表的なやり方
**スクラム**
| 役割・イベント | 説明 |
| --- | --- |
| プロダクトオーナー | 何を作るかを決める。作りたい機能の一覧（**プロダクトバックログ**）に優先順位を付ける |
| スクラムマスター | スクラムがうまく進むように支える |
| 開発者 | 実際に作る |
| デイリースクラム | 毎日の短い打合せ（昨日やったこと・今日やること・困っていること） |
| スプリントレビュー | スプリントの最後に、できたものを見てもらう |
| レトロスペクティブ | スプリントの最後に、進め方を振り返る |

**XP（エクストリームプログラミング）**
- **ペアプログラミング**：2人で1台のパソコンを使って作る
- **テスト駆動開発**：先にテストを書き、それに合格するようにプログラムを作る
- **リファクタリング**：動きを変えずに、プログラムの中身を読みやすく整理する

#### その他の進め方
- **プロトタイピング**：試作品を早く作って、お客さんに見てもらい、要望をはっきりさせる
- **DevOps**：開発する人と運用する人が協力して、素早く何度もリリースする

### ② 要件定義と設計

#### 要件（お客さんの要望）
- **機能要件**：何ができるか（例：商品を検索できる）
- **非機能要件**：どれくらいの品質で動くか（例：3秒以内に表示する、24時間止まらない）

#### UML（設計図の書き方）
| 図 | 表すもの |
| --- | --- |
| ユースケース図 | 誰（利用者）が、システムで何をするか |
| クラス図 | クラス（データと処理のまとまり）と、その関係 |
| シーケンス図 | オブジェクトどうしのやり取りを、時間の順に |
| アクティビティ図 | 処理の流れ（フローチャートに近い） |
| ステートマシン図 | 状態と、その変わり方 |

### ③ オブジェクト指向

#### イメージ
データと、そのデータを扱う処理を、1つの「もの（**オブジェクト**）」としてまとめて考える方法です。オブジェクトの設計図を**クラス**、設計図から作った実物を**インスタンス**といいます。
例：「犬」クラスから、「ポチ」「タロウ」というインスタンスを作る。

| 用語 | 意味 | 例 |
| --- | --- | --- |
| カプセル化 | データと処理をまとめ、中の作りを外から見えなくする | テレビの中の回路を知らなくても、リモコンで操作できる |
| 継承 | 親のクラスの性質を、子のクラスが引き継ぐ | 「動物」の性質を「犬」が引き継ぐ |
| 多態性（ポリモーフィズム） | 同じ命令でも、クラスによって違う動きをする | 「鳴け」で、犬はワン、猫はニャー |

- **汎化**：共通の性質をまとめて親クラスを作ること（「犬は動物の一種」＝ is-a の関係）
- **集約**：部品の関係（「タイヤは車の一部」＝ part-of の関係）

### ④ モジュールの設計

プログラムを、部品（**モジュール**）に分けて作ります。よい部品の条件は2つです。
- **結合度は弱く**：部品どうしが、できるだけ関係し合わない（1つを直しても他に影響しない）
- **強度（凝集度）は強く**：1つの部品の中身が、1つの目的にまとまっている

> **覚え方**：「結合は弱く、強度は強く」。いちばん良い結合は、必要なデータだけを引数で渡す「データ結合」。

### ⑤ テスト

#### テストの順番
1. **単体テスト**：部品（モジュール）1つずつ
2. **結合テスト**：部品をつなげて
3. **システムテスト**：システム全体として
4. **運用テスト（受入れテスト）**：お客さんが、実際の使い方で

#### ブラックボックステストとホワイトボックステスト
- **ブラックボックステスト**：中身を見ずに、入力と出力が仕様どおりかを確かめる
- **ホワイトボックステスト**：中身（プログラムの分かれ道）を見て、全部の道を通るように確かめる

#### テストデータの選び方（ブラックボックス）
「入力は1以上100以下」という仕様の場合
- **同値分割**：同じ動きをするグループに分け、各グループから代表を1つ選ぶ
　→ 0以下（エラー）、1〜100（正常）、101以上（エラー）から、例えば −5、50、150
- **限界値分析**：グループの**境目**の値を選ぶ（間違いが起きやすいから）
　→ **0、1、100、101**

#### 網羅の基準（ホワイトボックス）
- **命令網羅**：全部の命令を、少なくとも1回は実行する
- **判定条件網羅（分岐網羅）**：全部の分かれ道で、「はい」と「いいえ」の両方を通る
- **複数条件網羅**：条件の組み合わせを全部試す

#### 結合テストの代役
- **スタブ**：まだできていない**下**の部品の代わり（上から順にテストするとき）
- **ドライバ**：まだできていない**上**の部品の代わり（下から順にテストするとき）

#### その他
- **回帰テスト（リグレッションテスト）**：プログラムを直したとき、直していない部分が壊れていないか確かめる
- **レビュー**：作ったものを人の目で確かめる（ウォークスルー、インスペクションなど）

### ⑥ 保守

完成したソフトウェアを直すことを保守といいます。
- **是正保守**：見つかったバグを直す
- **適応保守**：OS の更新など、環境の変化に合わせて直す
- **予防保守**：問題が起きる前に直しておく

### この章のまとめ

- ウォーターフォールは順番に、アジャイルは小さく繰り返す
- プロダクトオーナーはバックログの優先順位を決める。デイリースクラムは毎日の打合せ
- カプセル化は中を隠す、継承は引き継ぐ、多態性は同じ命令で違う動き
- 結合度は弱く、強度は強く
- 限界値分析は境目の値（1〜100 なら 0、1、100、101）
- スタブは下の代役、ドライバは上の代役
- 回帰テストは、直した後に他が壊れていないかの確認
